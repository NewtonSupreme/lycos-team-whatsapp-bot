# ERP 2.0 — Diseño de arquitectura

**Fecha:** 2026-09-05
**Estado:** diseño aprobado a nivel programa; cada fase requiere su propio spec + plan.

---

## 1. Qué estamos construyendo

Un ERP multi-tenant vendible como producto, compuesto por:

- Un **núcleo horizontal** genérico y potente (entidades, flujos, permisos, reportes configurables).
- **Packs verticales** instalables encima (taller automotriz, retail, servicios…), que son 100% configuración y cero código.
- Una **interfaz conversacional de primera clase**: todo lo que se puede hacer en pantalla se puede hacer hablando, con los mismos permisos y las mismas validaciones.

### Decisiones tomadas

| Decisión | Elección |
|---|---|
| Producto o interno | **Producto multi-tenant (SaaS)** |
| Mercado | **Núcleo horizontal + packs verticales** |
| Motor de configuración | **Híbrido: núcleo fijo tipado + capa dinámica encima** |
| Rol de la IA | **Interfaz de primera clase**, no copiloto |
| Base de código | **Nueva desde cero.** No se arrastra el sistema actual. |

### Por qué esto le gana a Odoo

Odoo no es mediocre por falta de recursos, sino por siete decisiones de arquitectura concretas. Cada una tiene su respuesta en este diseño:

| Falla de Odoo | Respuesta acá |
|---|---|
| Personalizar exige programador (Python + XML) | Configuración como datos, editable desde la UI |
| ORM mágico en runtime: lento, sin tipos, indepurable | Núcleo en tablas Postgres reales, tipadas e indexadas |
| Vistas como documentos XML, no componibles | Vistas como definiciones componibles sobre la capa semántica |
| Sin tiempo real | Realtime por defecto sobre el log de eventos |
| Multi-moneda asume tasas estables | Dinero como primitiva, con tasa histórica en cada monto |
| Cada upgrade rompe las personalizaciones | Personalizaciones son datos con precedencia, no forks |
| IA pegada encima | IA consume la misma capa semántica que dibuja la UI |
| ~300 modelos hechos a mano | **5 primitivas** que se componen |

## 2. Arquitectura en capas

```
┌──────────────────────────────────────────────────────────────┐
│  5. PACKS VERTICALES        taller · retail · servicios ...   │
│     (100% configuración, versionados, instalables)            │
├──────────────────────────────────────────────────────────────┤
│  4. INTERFACES        Web UI  │  Conversacional  │  API       │
│                    (las tres leen la misma capa semántica)    │
├──────────────────────────────────────────────────────────────┤
│  3. CAPA SEMÁNTICA                                            │
│     Significado legible por máquina de cada entidad, campo    │
│     y acción. Una definición, tres consumidores.              │
├──────────────────────────────────────────────────────────────┤
│  2. MOTOR DE EXTENSIÓN                                        │
│     Campos y entidades custom, vistas, flujos, reglas         │
│     por tenant, guardados como datos (sin deploy).            │
├──────────────────────────────────────────────────────────────┤
│  1. PRIMITIVAS       Partes · Ítems · Documentos ·            │
│     Movimientos · Eventos                                     │
├──────────────────────────────────────────────────────────────┤
│  0. FUNDAMENTO     multi-tenant · identidad · permisos ·      │
│     eventos inmutables · motor de reglas · dinero             │
└──────────────────────────────────────────────────────────────┘
```

### Tres reglas invariantes

**a) Permisos y validación viven en las capas 0–1, debajo de toda interfaz.**
La UI, el bot y la API pasan por el mismo portero. Es imposible que un canal pueda hacer algo que otro no. Esto elimina de raíz la clase de bug que ya se sufrió en el sistema actual, donde el bot (`WRITE_TAGS`) y la UI (`permisos`) tenían modelos distintos que se desincronizaron.

**b) La capa semántica es la única fuente de verdad.**
Genera la UI, define la API y arma las herramientas que recibe la IA. Cuando un tenant agrega un campo, los tres se enteran en el mismo instante. No hay prompts que actualizar.

**c) Todo cambio de estado es un evento inmutable.**
Auditoría, trazabilidad, deshacer y reportes históricos son consecuencias del diseño, no features a parchear después.

## 3. Las cinco primitivas (capa 1)

Todo negocio se reduce a estas cinco. Cada vertical es una composición distinta de las mismas piezas.

### PARTY — con quien transaccionás
```
party        (id, org_id, kind: person|company, name, identifiers[], ...)
party_role   (party_id, role, valid_from, valid_to, attrs)
party_contact / party_address
```
Los roles son adjuntos, no horneados en el tipo. Una persona puede ser cliente, empleado y proveedor **a la vez** sin contradicción ni registros duplicados. Odoo usa `res.partner` con decenas de banderas booleanas; ese es el origen de su desorden.

### ITEM — lo que vendés, stockeás o consumís
```
item           (id, org_id, kind: good|service|kit|labor, sku, name, uom, tracking)
item_variant   (atributos sin explosión de tablas)
item_component (kits y despiece, auto-referencial)
```
Bienes y servicios comparten precio, impuesto y comisión. Separarlos fue un error de Odoo.

### DOCUMENT — la forma universal de toda transacción
```
doc_type       (CONFIGURABLE: presupuesto, orden de trabajo, factura, compra,
                remito, nota de crédito, transferencia… cada uno con su
                máquina de estados definida como datos)
document       (id, org_id, doc_type_id, number, party_id, state, currency, totals)
document_line  (document_id, item_id, qty, unit_price, discounts, taxes)
document_link  (from_doc, to_doc, relation: convierte_en|factura|devuelve|paga)
```
Presupuesto → orden → factura → pago es **una sola forma** con reglas distintas. Odoo tiene modelos separados con lógica duplicada. Acá un vertical inventa tipos de documento nuevos sin escribir código.

### MOVEMENT — stock y dinero son lo mismo
```
movement (id, org_id, kind: stock|cash, account_from, account_to,
          item_id?, qty?, amount?, currency, rate, occurred_at, document_id?)
```
Partida doble para ambos. Transferencias entre sedes, ventas, pagos, nómina y egresos son todos movimientos entre cuentas o ubicaciones. Los reportes se **derivan**, no se mantienen. Odoo pega la contabilidad por separado y las cifras derivan.

### EVENT — la verdad inmutable
```
event (id, org_id, actor_id, actor_kind: user|bot|system|integration,
       verb, subject_type, subject_id, payload, occurred_at,
       causation_id, correlation_id)
```
Auditoría, deshacer, reportes históricos, depuración y contexto para la IA salen todos de acá.

## 4. Dinero como primitiva

Dado el contexto latinoamericano con inflación y tasas volátiles, esto no es un campo: es una primitiva del núcleo. Es donde el producto es **categóricamente superior** a cualquier ERP europeo o norteamericano.

- Todo monto guarda: `amount_minor` (entero), `currency`, `rate_to_base`, `rate_source`, `rate_at`.
- **Nunca** se usa punto flotante. **Nunca** se convierte de forma perezosa.
- Un "precio" no es una columna: es el resultado de un **motor de resolución** en función de (ítem, parte, fecha, moneda, cantidad, canal).
- Las tasas históricas son ciudadanas de primera clase.
- Un reporte se puede correr "en USD a tasa de hoy" o "en USD a tasa del momento de cada transacción" — ambas son correctas y ambas hacen falta.

## 5. Multi-tenancy (decisión de ingeniería)

**Esquema compartido + `org_id` en cada tabla + Row Level Security de Postgres.**

- Una sola migración, un solo deploy.
- RLS se aplica **en la base**, no en el código: un bug de aplicación no puede filtrar datos entre tenants.
- Escape hatch: un tenant grande se puede mover a base dedicada más adelante sin tocar la aplicación, porque todo acceso ya está acotado por organización.
- **Se descarta esquema-por-tenant**: migrar cientos de esquemas es un infierno operativo conocido.

**RLS activo en todas las tablas desde el día uno, sin excepciones.** El sistema actual tiene 13 tablas con RLS apagado; ese error no se repite.

## 6. Motor de extensión (capa 2)

```
entity_def    entidades custom por tenant
field_def     campos custom sobre entidades del núcleo o custom
view_def      cómo se renderiza (lista, formulario, kanban, calendario)
workflow_def  máquinas de estado como datos (estados, transiciones, guardas, efectos)
rule_def      validación, automatización, precios, comisiones
action_def    qué se puede hacer y con qué permiso
```

**Almacenamiento:** los valores de campos custom viven en una columna `ext` (JSONB) sobre las tablas del núcleo, con índice GIN. Lo común es veloz porque es una columna real; lo raro es posible porque es dinámico. Una extensión que se vuelve crítica se puede **promover** a columna real más adelante.

**Las reglas no se evalúan con `eval`.** Se compilan a un AST seguro evaluado en proceso. Determinista, testeable y sin ejecución de código arbitrario de un tenant.

## 7. Capa semántica (capa 3) — el diferenciador

Cada entidad, campo y acción declara su significado:

- Etiqueta y **sinónimos** por idioma y por región (`placa` / `matrícula` / `patente`)
- Tipo semántico (dinero, cantidad, fecha, referencia a parte…)
- Descripción de intención
- Permiso requerido
- Ejemplos de uso conversacional

**Tres consumidores de la misma definición:**

1. **Generador de UI** — dibuja formularios y listas desde los `field_def`.
2. **Runtime de IA** — construye las *tool definitions* del modelo **dinámicamente por tenant y acotadas a los permisos del usuario que habla**. El modelo recibe herramientas tipadas, no un prompt gigante con una lista de tags.
3. **API** — REST/GraphQL generada desde las mismas definiciones.

Esto es lo que hace la interfaz conversacional real y no un truco: cuando un tenant agrega un campo "garantía", el bot sabe hablar de garantías ese mismo segundo. Un pack vertical trae su vocabulario conversacional gratis.

---

## 8. Packs verticales (capa 5)

Un pack es un bundle versionado y firmado de: tipos de documento, taxonomías de ítems, definiciones de campos, flujos, reglas, vistas, reportes, roles, datos semilla y vocabulario conversacional.

**Las personalizaciones del tenant se superponen al pack con precedencia y sobreviven a los upgrades**, porque son datos, no forks. Esa es la respuesta directa a "cada actualización de Odoo te rompe lo que personalizaste".

---

## 9. Stack (decisión de ingeniería)

- **Postgres** — RLS, JSONB, replicación lógica para el log de eventos.
- **TypeScript de punta a punta** — tipos compartidos desde la base hasta las herramientas de la IA.
- **Next.js (App Router)** para la web.
- **Capa de servicios real**: la lógica de dominio vive en módulos puros, no en route handlers. Esto es lo que evita repetir el `webhook/route.ts` de 296 KB del sistema actual.
- **Motor de reglas determinista** sobre AST seguro.
- **Log de eventos en Postgres** con patrón outbox para integraciones.
- **LLM vía tool-calling** contra los esquemas generados por la capa semántica.

**Testing:** la capa de dominio son funciones puras sobre datos, 100% testeable por unidad. Cada pack vertical trae sus tests de contrato.

## 10. Fases

Cada fase es un sub-proyecto con su propio spec y su propio plan de implementación.

| Fase | Contenido | Criterio de terminado |
|---|---|---|
| **0. Fundamento** | Multi-tenant + RLS, identidad, permisos, log de eventos, primitiva de dinero | Sin UI. Suite de tests que prueba aislamiento entre tenants y que ningún canal saltea el portero de permisos. |
| **1. Primitivas + UI mínima** | Partes, Ítems, Documentos, Movimientos. UI genérica generada desde `field_def`. | Un flujo de venta completo funciona de punta a punta. |
| **2. Motor de extensión** | Campos y entidades custom, vistas, flujos, reglas. | Un usuario no programador agrega un campo y un estado nuevo, y aparecen en la UI sin deploy. |
| **3. Capa semántica + IA** | Generación de herramientas, runtime conversacional, canal WhatsApp. | Todo lo que se hace en pantalla se puede hacer hablando, con los mismos permisos. |
| **4. Pack vertical: Taller** | Todo lo que necesita Lycos Team, expresado como configuración. Migración de datos reales. | **Puerta de validación del programa.** |
| **5. Capa SaaS** | Onboarding, planes, cobro, panel de tenant, distribución de packs. | Un cliente nuevo se registra y opera sin intervención manual. |
| **6+. Más verticales** | Retail, servicios, restaurante… | Cada pack se construye sin tocar el núcleo. |

### La fase 4 es la puerta de validación

Si el taller de Lycos Team **no puede correr sobre configuración pura**, el motor está mal diseñado y se corrige antes de construir un solo vertical más. Es la prueba honesta de que la tesis se sostiene, y se hace con un negocio real y datos reales antes de vendérselo a nadie.

## 11. Qué NO entra (YAGNI)

Explícitamente fuera de alcance hasta que exista demanda real y comprobada:

- Manufactura y planificación de producción (MRP)
- E-commerce propio (sí integraciones)
- Contabilidad de partida doble con plan de cuentas fiscal completo por país — el núcleo de movimientos la habilita, pero el cumplimiento fiscal por país es un pack aparte
- App móvil nativa (la web responsive cubre el caso hasta que se demuestre lo contrario)
- Marketplace público de packs de terceros

---

## 12. Riesgos conocidos

| Riesgo | Mitigación |
|---|---|
| El motor genérico termina siendo potente y vacío (la trampa de Odoo) | La fase 4 obliga a que un negocio real corra sobre configuración pura antes de seguir |
| La capa dinámica degrada el rendimiento | Núcleo en columnas reales; JSONB solo para lo custom; promoción a columna real cuando pesa |
| La IA ejecuta acciones destructivas | El portero de permisos es el mismo para todos los canales; acciones sensibles requieren confirmación por política configurable |
| Complejidad del motor de reglas | AST determinista, sin `eval`, con cobertura de tests exhaustiva |
| Alcance del programa | Fases independientes, cada una entrega valor por sí sola |
